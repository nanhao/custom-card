# Architecture Design — Structured Logging for Self-Play

## 1. Motivation

Add machine-parseable structured logging to the entire self-play lifecycle (`scripts/selfplay.py` → `SelfPlayRunner`). Logs enable post-hoc correctness verification, reproducibility analysis, and automated script parsing. The logging infrastructure is a **shared backend facility**: the logger package and config are designed for reuse by any backend script, not just self-play.

## 4. Dependency Rule

```
scripts/selfplay.py      ──reads──▶ config/backend.json (logging section)
scripts/selfplay.py      ──calls──▶ LoggerBuilder.init(enabled, log_dir)
                                     │
                                     └──▶ creates singleton StructuredLogger
                                              └──▶ writes ──▶ {project_root}/logs/{yyyy}-{mm}-{dd}.log

app/SelfPlayRunner       ──calls──▶ LoggerBuilder.get_logger()
                                     └──▶ log(level, event, **kwargs)

log/StructuredLogger     ──depends─▶ nothing (stdlib only: os, datetime, threading, uuid)
log/LoggerBuilder        ──depends─▶ StructuredLogger (same module)
```

`StructuredLogger` and `LoggerBuilder` depend on nothing except Python stdlib. Any module anywhere can access the singleton logger via `LoggerBuilder.get_logger()` without threading it through constructors or method parameters.

Refer to [class_diagram.puml](diagrams/class_diagram.puml).

## 5. Key Design Decisions

**D1 — `StructuredLogger` is a generic, low-level logging facility.** It knows nothing about games, cards, or AI. It provides a single `log(level, event, **kwargs)` method. Callers choose their own event names and message fields. This keeps the logger reusable across the entire backend.

**D2 — Pipe-delimited log format.** Format: `{timestamp} | {traceId} | {pid} | {tid} | {level} | {event} | {message}`. Chosen over JSON because it is easy to append line-by-line without structural overhead, and easy to parse with `split(" | ")`. The message field uses `key=value` pairs for structured data within each event.

**D3 — Per-day log rotation.** File name is `{yyyy}-{mm}-{dd}.log`, computed at each write call. If the date changes mid-run, logs automatically roll to a new file. No in-process file handle caching — the file is opened and closed per write to avoid stale handles across long runs.

**D4 — Logger is globally accessible via `LoggerBuilder` singleton.** `LoggerBuilder.init(enabled, log_dir)` is called once at startup (in `scripts/selfplay.py`). Any module anywhere then calls `LoggerBuilder.get_logger()` to get the singleton `StructuredLogger` instance. No need to thread the logger through constructors or method parameters. When disabled, the singleton still exists but all `log()` calls are no-ops.

**D5 — Human-readable `print()` output is preserved unchanged.** Structured logs go to file only. Console output remains the existing per-game summary lines and final aggregate summary. This keeps the CLI experience unchanged while adding audit capability.

**D6 — traceId is an 8-character hex string.** Generated by `StructuredLogger.__init__()` via `uuid4().hex[:8]`. Short enough to be readable, long enough to avoid collisions across concurrent runs. Exposed as a read-only property.

**D7 — Config is shared across the backend.** `config/backend.json` is a general backend configuration file. The logging section (`logging.enabled`, `logging.log_dir`) is one part of it. Future backend-wide settings (e.g., database, API) will live in the same file.

**D8 — Log directory is project-root-relative.** `log_dir` defaults to `"logs"` and is resolved relative to the project root. Log files are written to `{project_root}/logs/{yyyy}-{mm}-{dd}.log`.

**D9 — `LoggerBuilder.init()` must be called before any `get_logger()`.** Calling `get_logger()` before `init()` raises `RuntimeError`. This ensures the logger is always properly configured before use.

**D10 — Event names are namespaced by consumer to avoid collisions.** Each script/module uses a prefix, e.g. `selfplay.`, `training.`, `analysis.`. The `StructuredLogger` is prefix-agnostic — it writes whatever event string it receives. Namespacing is a caller convention, not enforced by the logger. This ensures events from different scripts never collide.

## 6. Logged Events (Self-Play Lifecycle)

Event names use the `selfplay.` namespace prefix. For the self-play script, the following events are logged:

| Event | Level | When | Message Fields |
|-------|-------|------|----------------|
| `selfplay.run_start` | INFO | CLI starts | ai1, ai2, game_count, temperature, temp_step, temp_side, temp_seed, sample_output |
| `selfplay.ai_validated` | INFO | AI names validated | ai1, ai2 |
| `selfplay.model_loaded` | INFO | Model loaded/cached | ai_name |
| `selfplay.game_start` | INFO | Each game begins | game_idx, game_count |
| `selfplay.round_action` | DEBUG | Both AIs' cards selected | round, card1, card2, temp1, temp2 |
| `selfplay.round_result` | DEBUG | Round damage resolved | round, dmg1, dmg2, hp1, hp2 |
| `selfplay.game_end` | INFO | Each game ends | game_idx, winner, rounds |
| `selfplay.sample_write` | DEBUG | Samples flushed | game_idx, count |
| `selfplay.error` | ERROR | Any exception caught | error_type, msg, game_idx, round |
| `selfplay.run_end` | INFO | Run complete | total_games, ai1_wins, ai2_wins, draws, avg_rounds |
